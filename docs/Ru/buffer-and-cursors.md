# Буфер и курсоры

## Модель буфера

Устройство буфера описано отдельным документом: [Буфер Claxis](buffer.md) — `Original`, `Add Arena`, линейная история и плоское текущее состояние из сегментов. Здесь только то, что живёт поверх него: курсор, отмена, кодировки, сохранение.

## Курсор

Курсор — пара точек.

```rust
struct Cursor {
    anchor: Position, // якорь — неподвижный конец
    head: Position,   // голова — активный конец
}
```

Если `anchor == head`, это точка. Если не равны — выделение между якорем и головой.

Выделение получается бесплатно из модели курсора: отдельный механизм выделения на уровне данных не нужен, хватает двух позиций вместо одной.
Работает это так, при любом изменении якорь остаётся в позиции начала изменений, голова движется до момента конца изменений. Этот диапазон и записывается как одно изменение.

## Символы и графемы

Буфер **байтовый** и про UTF-8 не знает ничего: он оперирует `u32`-позициями
в байтах и режет по ним без проверок. Символы и графемы считаются **на лету и
только локально** — в курсорном слое, для того, что реально видно на экране.
Документ целиком не декодируется никогда, в том числе при открытии файла.

### Почему это работает без таблиц

UTF-8 самосинхронизирующийся: у ведущего байта символа верхние биты не `10`,
у байтов продолжения — `10`. Значит границу символа можно найти проходом
вперёд в любом месте, без состояния и без таблиц. Это и делает локальный
подсчёт символов дешёвым.

### Инварианты

1. **Границы символов — забота курсорного слоя, не буфера.** Ни одна правка не
   должна приходить с позицией внутри многобайтовой последовательности.
   Считается, что все диапазоны приходят извне через курсорный слой и
   приводятся к границам символов там.
2. **Одна функция приведения к границам, звать её везде.** Загрузка файла,
   поиск с заменой, вставка из буфера обмена, команды — любой путь, где
   диапазон приходит снаружи. Забытый путь даёт невалидный UTF-8.
3. **`read_range` режет по любому байту** без паники и без проверок — так и
   должно быть: поиск и подсветка режут произвольно.

### Поиск и подсветка

Поиск работает по байтам: подстрока UTF-8 находится корректно, а подсветка —
это байтовый диапазон, который красится как есть. Декодировать текст для
поиска не нужно.

### Графемы и ширина

Терминал видит не символы, а **ячейки**: строка плюс колонки. Одна ячейка —
это графема, и она может занимать одну или две колонки. Комбинирующиеся знаки,
восточноазиатские двухколонковые символы, эмодзи с ZWJ — всё это одна ячейка
с одной шириной.

Графемы, как и символы, считаются локально: нужно знать только правила склейки
и правила ширины, хранить их постоянно не надо. Ширина считается по модели
терминала, а не по числу байт и не по числу символов.

## Undo/redo

История группируется по событиям.

| Механизм | Правило |
|---|---|
| Пауза ввода | Непрерывный набор склеивается в одну запись, пауза длиннее таймаута открывает новую |
| Границы слов | Пробел — разделитель: слово вставляется и удаляется как одна единица |
| Тип события | Вставка — отдельный тип со своими правилами группировки |
| Границы команд | Одна выполненная команда — одна запись, включая повтор `3dd` |

Правила настраиваются поверх базовой модели: таймаут, символы-разделители и типы событий задаются конфигом. Формат записей проектируется с учётом сериализации, чтобы историю можно было восстановить между запусками — это развитие, не MVP.

Отмена применяется к документу напрямую и не зависит от режима: она одинакова в командном режиме, в режиме edit и в командном вводе под модификатором.

## Кодировки и переводы строк

Поддерживаются UTF-8, UTF-16 и Latin-1. Кодировка определяется при открытии, файл сохраняется в исходной кодировке: открыли Latin-1 — сохранился Latin-1. Конвертация при сохранении не выполняется.

Переводы строк: `LF`, `CRLF`, `CR`. BOM распознаётся при чтении и воспроизводится при записи.

## Сохранение

Документы хранятся только как обычный текст. `git diff` читает изменения напрямую, файл виден через `cat` и открывается любым другим редактором. Никаких метаданных, сжатия или собственного формата внутри документа.

Сохранение идёт через временный файл с последующим `rename`. Падение питания в середине записи не оставляет наполовину испорченный документ: либо старая версия, либо новая.

Служебные данные — backup, последняя рабочая версия конфига, журнал восстановления — хранятся в бинарном формате, который позволяет дописывать без перезаписи всего файла.
