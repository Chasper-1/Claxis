# Буфер Claxis

## 1. Назначение

Буфер Claxis предназначен для хранения и редактирования текста с поддержкой:

* вставки;
* удаления;
* замены;
* undo/redo;
* последующего хранения истории на диске.

Основная идея — **не изменять исходные данные физически**, а хранить новые данные отдельно и описывать текущее состояние документа через последовательность сегментов.

Буфер состоит из пяти частей:

```text
Original    исходный текст при загрузке
Added       растущий буфер всего вставленного текста
Add Arena   метаданные правок, 16 байт на правку
History     два стека номеров записей арены
Current     материализованное состояние документа
```

`Current` — единственное материализованное состояние. Всё остальное — данные и хронология.

---

## 2. Original

`Original` — исходное содержимое документа.

Оно:

* immutable;
* не изменяется после загрузки;
* используется как источник сегментов текущего документа;
* не копируется при обычных операциях редактирования.

Пример:

```text
Original:
abcdefghijklmnopqrstuvwxyz
```

После любых изменений исходные байты остаются на месте. Удаление лишь убирает участок из чтения.

---

## 3. Added

`Added` — растущий буфер всего текста, который когда-либо вставляли.

Он не ограничен ареной. Каждая вставка дописывает байты в конец, `text_off` — смещение, по которому сегмент будет читать этот текст.

Пример:

```text
Original:
abcdefghijklmnopqrstuvwxyz

Added:
HELLO1234
         ↑
       смещение 5
```

Байты из `Added` физически не удаляются: ни при удалении, ни при undo, ни при пересборке.

---

## 4. Add Arena

`Add Arena` — append-only хранилище **метаданных** правок. Текста здесь нет.

Одна запись — 16 байт:

```rust
Record {
    kind: Kind,   // Insert или Delete
    pos: u32,     // где
    len: u32,     // сколько байт
    data: u32,    // где лежат данные правки
}
```

`data` означает разное по виду правки:

* **вставка** — смещение вставленного текста в `Added`;
* **удаление** — смещение отложенных сегментов относительно начала отложенной области.

### Ёмкость

```text
ARENA_CAPACITY = 128 КиБ
Record         = 16 байт
записей        = 8192
```

Арена ограничена, потому что снапшот обнуляет историю, а при выходе из редактора она всё равно не нужна. Глубина отмены в 8192 правок никого не ограничивает.

При заполнении вызывается снапшот: документ собирается в текст, текст становится новым `Original`, арена переиспользуется. Подробности в §14.

### Почему метаданные, а не текст

Текст вставок не ограничен ареной, иначе большая вставка не помещалась бы. Ограничиваются только записи — а их мало, и именно они должны быть ограничены.

Записи не удаляются при изменении документа. Место указывается идентификатором и диапазоном:

```text
AddId = 42
range = 100..140
```

`Current` может ссылаться на этот диапазон независимо от того, сколько раз данные вокруг него менялись.

---

## 5. History

История — **два стека номеров записей арены**:

```text
undo_stack
redo_stack
```

Активные изменения в `undo_stack`, отменённые — в `redo_stack`. Механика LIFO: последний пришёл — первый ушёл.

```text
1. Новая правка кладётся в вершину undo_stack.
2. Undo снимает запись с вершины undo_stack и кладёт в вершину redo_stack.
3. Redo снимает запись с вершины redo_stack и кладёт обратно в undo_stack.
4. Порядок записей внутри стеков никогда не переупорядочивается.
```

Оба стека содержат записи одного типа. Запись не меняет формы при переходе между стеками.

Redo — буквально отмена отмены: та же запись движется обратно.

### Новое изменение после undo

```text
undo_stack:
[A, B]

redo_stack:
[C]
```

Создаётся `D`:

```text
undo_stack:
[A, B, D]

redo_stack:
[]
```

Redo-ветка отбрасывается: после undo новые правки ветвят документ по другой траектории, а redo предполагает, что повторяется ровно то, что было отменено.

Физические данные отменённой `C` при этом **не трогаются**. Очистка касается только ссылок — номеров записей в стеках.

### Отдельного описания отмены нет

Запись хранит только **что произошло**. Как её обратить выводится из самой записи:

```text
Insert(pos, len, data) → отмена это Delete(pos, len)
Delete(pos, len, data) → отмена это возврат отложенных сегментов в чтение
```

Никаких «характеристик перестановки», «ссылок для переключения» или копий узлов в истории не хранится.

---

## 6. Current

`Current` — материализованное состояние документа: **плоская последовательность сегментов**.

Он не является отдельным источником данных. Данные лежат в `Original` и `Added`, `Current` — готовый план чтения.

Сегмент — 12 байт, три `u32`:

```rust
Segment {
    src: u32,   // 0 = Original, 1 = Added
    off: u32,   // смещение внутри источника
    len: u32,   // сколько байт
}
```

Байтов он не содержит — указывает, откуда и сколько их взять.

### Ссылок нет

Сегменты лежат в буфере **по порядку документа**. Номер сегмента и есть его позиция, поэтому шаг — это индекс плюс или минус один:

```text
segments[i] → segments[i + 1] → segments[i + 2]
```

Ни `next`, ни `prev` не нужны: они выводимы из индекса. Хранить их было бы дублированием.

Плата за это известна и измерена: вставка в середину двигает хвост. Читается это как `copy_within` — один проход, всё разом.

### Пример

```text
Original:
abcdefghijklmnopqrstuvwxyz
```

После вставки `"HELLO"` на позицию 10:

```text
[
    Segment { src: 0, off: 0,  len: 10 },
    Segment { src: 1, off: 0,  len: 5  },
    Segment { src: 0, off: 10, len: 16 },
]
```

Документ читается как:

```text
abcdefghijHELLOklmnopqrstuvwxyz
```

### Current всегда плоский

Даже если изменения логически вложены друг в друга, состояние остаётся плоской последовательностью:

```text
Original → Add #1 → Add #2 → Add #1 → Original
```

Читатель не разбирает зависимости, он идёт по сегментам подряд. Глубина логической вложенности на алгоритм чтения не влияет.

## 7. Позиционирование

Позиция курсора хранится **в байтах**. Рядом лежит результат последнего прохода — номер сегмента и смещение внутри него, чтобы следующий поиск не начинался с нуля.

Чтобы дойти до новой позиции, считается разница:

```text
разница = новая позиция - прошлая позиция
```

* `разница > 0` — идём вперёд, индекс растёт, длины **прибавляются**;
* `разница < 0` — идём назад, индекс убывает, длины **вычитаются**.

Оба направления одинаково дешёвые: шаг это индекс, а не обход дерева. Обход от начала не нужен никогда.

```rust
while left > 0 {
    let room = segs[idx].len - off;
    if left < room { off += left; break; }
    off += room;
    left -= room;
    if left == 0 { break; }
    idx += 1;
    off = 0;
}
```

## 8. Вставка

`insert(pos, data)`:

1. текст дописывается в `Added`, `text_off` — смещение;
2. в арену кладётся запись `Insert(pos, len, text_off)`;
3. `Current` находит позицию, разрезает сегмент и ставит новый между частями.

```text
Original(0..26), вставка "XY" на позиции 3:

было:  [ Original(0, 26) ]
стало: [ Original(0, 3), Added(text_off, 2), Original(3, 23) ]
```

Исходный сегмент разрезан на два, между ними вставлен новый. Байты `Original` не изменились.

Позиция может попасть ровно на конец сегмента — это обычное разбиение, хвост при этом пустой и в последовательность не входит.

---

## 9. Удаление — не отмена

**Удаление исключает диапазон из чтения. Байты никуда не исчезают.**

`delete(pos, len)`:

1. `Current` находит сегменты, покрывающие диапазон;
2. удаляемые части сегментов копируются в **отложенную область** — хвост буфера за живыми сегментами;
3. оставшиеся неразрезанные края остаются в чтении;
4. в арену кладётся запись `Delete(pos, len, смещение_отложенных)`.

Пример. Удаление `70..90` из `Original(50..100)`:

```text
стало:
[ Original(50, 20), Original(90, 10) ]
```

Исходные байты `50..100` остались в `Original`. Из чтения ушёл участок `70..90`.

Отложенные сегменты описывают **ровно удалённый диапазон и ни байтом больше**. Они лежат в буфере и никуда не делятся, поэтому отмена — это просто возврат их в чтение:

```rust
fn restore_deleted(&mut self, pos: u32, parked: u32, len: u32)
```

Текст удалённого не копируется никуда: он уже лежит в `Original` или `Added`, отложенные сегменты на него ссылаются.

### Граница хвоста

Живые сегменты — `segs[0..count]`, отложенные — `segs[parked_from..]`. Когда живая область дорастает до отложенной, отложенная переезжает целиком. Смещения в записях арены **относительные** к началу отложенной области, поэтому переезд их не ломает.

---

## 10. Отмена и повтор

```text
undo:
    Insert → current.apply_delete(pos, len)
    Delete → current.restore_deleted(pos, data, len)

redo:
    Insert → current.apply_insert(pos, data, len)
    Delete → current.apply_delete(pos, len)
```

Обе операции — та же обычная правка, только в обратную сторону. Никакой отдельной машинерии.

Стек при этом даёт порядок: записи снимаются с вершины, поэтому к моменту отмены состояние документа в точности то, которое было сразу после этой правки.

```text
History:
A B C D

Current = A + B + C + D

после undo D:
undo: A B C
redo: D
Current = A + B + C
```

---

## 11. Замена

Замена — это удаление и вставка, никакой отдельной модели:

```text
replace(pos, len, data) == delete(pos, len) + insert(pos, data)
```

Старое физически цело и лежит под новым.

---

## 12. Пересборка — восстановление

`Current` — кеш. Если он потерян или повреждён, данные документа не должны потеряться. Он строится заново из `Original` и активной истории:

```text
Original
   +
active history (undo_stack по порядку)
   ↓
Current
```

Это **линейный проход**: одна операция на запись, действия заранее известны — позиция, длина, смещение.

**В редакторе `rebuild` не вызывается.** В коде вызовов нет ни одного, кроме тестов и бенчей. Это аварийный путь, а не горячий, и оптимизировать его незачем.

Обычная работа идёт через `apply_insert` и `apply_delete`, которые меняют `Current` на месте.

Пересборка вызывается в тестах как эталон: результат обязан совпадать с инкрементальным состоянием.

---

## 13. Память выделяется один раз

Буфер сегментов выделяется целиком при создании `Current` и больше не перевыделяется:

```text
ARENA_RECORDS  = 8192                    записей арены
SEG_CAPACITY   = 1 + 2 * ARENA_RECORDS    = 16385 сегментов
память         = 16385 * 12               ≈ 192 КиБ
```

Каждая запись арены добавляет в буфер не больше двух сегментов: вставка режет один на три, удаление откладывает края. Плюс один сегмент на исходный текст.

Буфер **не сжимается**. Удалённые сегменты остаются в нём, `parked` только растёт и обнуляется лишь в пересборке. Поэтому в горячем пути:

* `resize` только заполняет уже выделенную память;
* временные буферы не отдаются и не удаляются;
* аллокаций нет вовсе.

Проверено счётчиком глобального аллокатора:

```text
выделений на одну вставку: 0
выделений на одно удаление: 0
выделений на пересборку: 0
```

Переполнение ловится `debug_assert` по `SEG_CAPACITY`.

## 14. Снапшот

`Snapshot` собирает документ в текст, текст становится новым `Original`, `Added` очищается, арена переиспользуется, `Current` строится заново от нового `Original`.

```rust
pub fn snapshot(&mut self) {
    let text = self.read();
    self.original = text;
    self.added.clear();
    self.arena.reset();
    self.current = Current::from_original(&self.original);
    // TODO: переезд истории на новый исходный текст — см. отчёт.
    self.history = History::default();
}
```

### Не сделано

История обнуляется, а не переносится на новый `Original`. То есть после снапшота отменяются только правки текущего цикла, более ранние — нет.

Формат переезда истории не выбран. Договорённость: переезд будет записан в буфер отдельной частью, а не выбран сейчас. Что именно туда класть — `Current` целиком, снапшот сегментов или просто текст — не определено.

Пока это сделано, автоматический вызов снапшота по заполнении арены **рвёт Ctrl-Z**. Это известное и не исправленное поведение.

## 15. Сложность и замеренные цифры

Архитектура не фиксирует конкретную структуру хранения. Она требует только, чтобы `Current` был плоской материализованной последовательностью сегментов. В реализации это `Vec<Segment>`.

Полное чтение документа неизбежно `O(document size)`, это не `O(1)`.

Плоский массив означает: вставка в середину двигает хвост. Это не накладной расход, а цена contiguity, и она линейна по числу сегментов после точки вставки.

Измерено на 128 КиБ арены:

| операция | 2 000 сегментов | 16 000 сегментов |
|---|---|---|
| вставка в середину | 28–50 нс | 28–83 нс |
| вставка в конец | 18–27 нс | 18–29 нс |
| движение курсора | 30–43 нс | 28–57 нс |
| чтение 500 КБ | 15–26 мкс | 36–63 мкс |
| широкое удаление | 14–17 мкс | 5.7–12 мкс |

Чтение 500 КБ через 16 000 сегментов — около 36 мкс, это примерно 14 ГБ/с.

Сегментов больше 16 385 не будет: это предел арены. На пределе вставка в середину стоит микросекунды, а не десятки микросекунд.

## 16. Основные инварианты

### Original и Added

```text
Original не изменяется после загрузки.
Added только растёт, байты не удаляются.
```

### Add Arena

```text
Arena append-only, ёмкость фиксирована.
Запись содержит только метаданные, текста нет.
data указывает в Added для вставки, в отложенные сегменты для удаления.
```

### History

```text
История линейна, два стека номеров записей.
Отдельного описания отмены не хранится.
Новая правка отбрасывает redo-ветку.
Очистка redo не трогает физические данные.
```

### Current

```text
Current плоский, без ссылок.
Сегменты идут по порядку документа, шаг это индекс.
Позиция курсора в байтах, движение по разности позиций.
Current не является source of truth.
```

### Delete

```text
Delete исключает диапазон из чтения.
Байты никуда не исчезают.
Отложенные сегменты описывают ровно удалённый диапазон.
Смещение отложенного относительное, переезд области его не ломает.
```

### Rebuild

```text
Current восстанавливается из Original + active History линейным проходом.
Результат совпадает с инкрементальным состоянием.
```

### Reading

```text
Reader читает сегменты подряд.
Reader не разбирает зависимости и не обходит историю.
```

### Память

```text
Буфер сегментов выделен один раз и не перевыделяется.
В горячем пути аллокаций нет.
```

## 17. Тестирование

Проверяются инварианты и семантика операций. 37 тестов покрывают:

```text
insert / delete / replace
undo / redo
undo → redo, undo → новая правка
вложенные вставки и удаления
delete через границы нескольких сегментов
delete всего документа и до конца
полный undo до оригинала, полный redo до состояния
rebuild после каждой правки == инкрементальное состояние
rebuild устойчив к повторам
дифференциальный тест против эталонной строки на псевдослучайных правках
переполнение арены: цикл снапшотов, текст и состояние не теряются
огромная вставка не ограничена ареной
серия правок и пересборок без перевыделения буфера сегментов
```

Отсутствие аллокаций в горячем пути проверялось счётчиком глобального
аллокатора; отдельного теста в наборе нет, из §13 это следует из того, что
буфер выделяется один раз при создании `Current`.

Особо важны операции через границы сегментов:

```text
Original | Add | Add | Original
          ↑
        delete
```

---

## 18. Долговременная история

Модель допускает вынесение старой истории на диск: снапшот становится новой базой, а после него живёт только активная часть истории.

Такой уровень над буфером не требуется для базовой реализации и сейчас не сделан. Связанный с ним вопрос — формат переезда истории при снапшоте, см. §14.

## 19. Итоговая модель

```text
                     ┌──────────────┐
                     │   Original   │
                     │  immutable   │
                     └──────┬───────┘
                            │
                     ┌──────▼───────┐
                     │     Added    │
                     │  растёт      │
                     └──────┬───────┘
                            │
                     ┌──────▼───────┐
                     │  Add Arena   │
                     │  128 КиБ     │
                     │  метаданные  │
                     └──────┬───────┘
                            │
                     ┌──────▼───────┐
                     │   History    │
                     │  undo / redo │
                     └──────┬───────┘
                            │
                            │ применяется по порядку
                            ▼
                     ┌──────────────┐
                     │   Current    │
                     │ flat, Vec    │
                     └──────┬───────┘
                            │
                            │ sequential read
                            ▼
                     ┌──────────────┐
                     │   Reader     │
                     │   Renderer   │
                     └──────────────┘
```

Главный принцип:

> **Added хранит вставленный текст, Add Arena хранит метаданные правок, Original хранит исходное состояние, History хранит порядок того, что произошло, а Current хранит готовый плоский план чтения текущего документа.**

Разделение этих ролей и есть основа буфера Claxis.
