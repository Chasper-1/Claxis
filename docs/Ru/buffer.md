# Буфер Claxis

## 1. Назначение

Буфер Claxis предназначен для хранения и редактирования текста с поддержкой:

* вставки;
* удаления;
* замены;
* undo/redo;
* выгрузки истории на диск снапшотами.

Буфер состоит из шести частей:

```text
Original   исходный текст при загрузке, immutable
Added      отдельный вектор всего вставленного текста
Arena      записи правок, ограничена, живёт в ней два стека: undo и redo
Record     одна правка: операция + диапазон (якорь .. голова)
Segment    ссылка на запись и на текст, байт и позиций не хранит
Current    кеш: дерево сегментов, порядок чтения, не больше 16K листьев
```

`Current` — кеш. Всё остальное — данные и хронология.

---

## 2. Original

`Original` — исходное содержимое документа.

Оно:

* immutable;
* не изменяется после загрузки;
* просто есть — источник байт для чтения;
* не копируется при обычных операциях редактирования.

После любых изменений исходные байты остаются на месте. Удаление лишь вырезает
участок из `Current` — из `Original` байты не пропадают.

---

## 3. Added

`Added` — отдельный вектор изменений: весь текст, который вставляли.

* В горячем пути `Added` **только дописывается**, ничего не меняется.
* Тексты вставок находятся в нём по ссылке из сегмента.
* Изменение одного правила: **если в `undo` приходит новая запись, а `redo`
  не пуст** — `redo` очищается, и тексты отменённых вставок удаляются из
  `Added`. Дыра закрывается перемещением памяти. Это быстро, потому что
  отменялись самые поздние вставки — они всегда рядом с концом `Added`.

При снепшоте `Added` переиспользуется заново (см. §11).

---

## 4. Arena

`Arena` — хранилище **записей правок**. Текста здесь нет.

Записи лежат в **блоках** фиксированного размера. Когда текущий блок
переполняется, под записи выделяется **новый блок** — записи не теряются и не
переприсваиваются: у каждой остаётся свой стабильный идентификатор. Пропуска
записей нет ни при каких обстоятельствах.

Внутри арены живут **два стека**:

```text
undo   все записи подряд, как в стеке
redo   только отменённые записи
```

### undo

В `undo` пишется **всегда и всё**: каждая правка кладёт сюда свою запись.

### redo

`redo` хранит только отменённые записи.

**Главное правило:** если `redo` не пуст, а в `undo` попадает новая запись —
`redo` очищается целиком, и тексты отменённых вставок удаляются из `Added`
(см. §3). Документ пошёл по другой траектории, повторять ровно то, что было
отменено, больше нечем и незачем.

### Размер блока

Один блок — фиксированный размер, выбранный из лесенки:

* от **32КБ** (минимум, 2К записей — запись 16 байт, для самых экономных)
  до **128КБ** — шаг **32КБ**;
* после 128КБ до **512КБ** — шаг **64КБ**;
* после 512КБ до **1МБ** (максимум) — шаг **128КБ**.

Когда подходит конец блока, выделяется следующий такого же размера. Снапшот
записи не вызывает: история уходит на диск явным снапшотом (§11).

---

## 5. Record — запись правки

Запись описывает **что произошло** — и всё. Операция несётся самой записью,
второй раз её писать не надо:

```rust
enum Record {
    // вставка: несёт ссылку на текст в Added
    Insert { anchor: u32, head: u32, text: u32 },
    // удаление: текста нет — оно ничего не добавляет, поэтому записи меньше
    Delete { anchor: u32, head: u32 },
}
```

* `anchor` — якорь, начало диапазона, всегда известен;
* `head` — голова, конец диапазона, всегда известна;
* `text` — ссылка на вставленный текст в `Added` (только у `Insert`).

Длина — `anchor - head`. Если значение выходит минусовым — оно просто
делается плюсовым (берётся по модулю), больше ничего не значит.

Знак не важен: направление операции говорит **сама запись**. `Insert`
означает «добавить», `Delete` — «забрать». Всё.

Нет ни ссылок на текст, ни общей длины: только **операция и диапазон**.
Диапазон записывается один раз при правке и больше не обновляется.

Для поиска прошлого или соседнего диапазона длина вычисляется из записи —
`anchor - head` по модулю, — а прибавляется или отнимается от записанного
значения в зависимости от того, вставка это или удаление.

---

## 6. Segment — сегмент

Сегмент — позиция, ссылка на текст и ссылка на запись:

```rust
Segment {
    record: RecordRef,   // ссылка на запись, u32
    pos:    u32,         // позиция, куда текст поставлен
    off:    u32,         // смещение в источнике
    len:    u32,         // сколько байт в этом сегменте
}
```

Ровно **16 байт**: четыре `u32` подряд, без хвоста выравнивания.

* `record` — ссылка на запись в арене;
* `pos` — позиция, куда текст был вставлен;
* `off`, `len` — где и сколько байт читать в источнике.

**Источника в сегменте нет** — он выводится из записи: `record == ORIGINAL_ID`
означает текст `Original`, любая другая запись — это `Insert`, и её текст лежит
в `Added`. Дублировать это в сегменте незачем, а именно лишнее поле раздувало
сегмент с 16 до 20 байт.

Каждый сегмент несёт **живой** текст. Сегментов-удалений не существует:
удаление вырезает сегменты из дерева (§9), запись об удалении остаётся в
стеках, но как сегмент в чтение не попадает.

---

## 7. Current

`Current` — **кеш**: дерево сегментов в порядке документа. Это готовый план
чтения: в каком порядке и что именно читать.

`Current` не является источником данных. Данные лежат в `Original` и `Added`,
`Current` — порядок, в котором эти данные дают текущий документ. Он собирается
**линейным проходом по записям** `undo` (см. §10).

Листья дерева идут слева направо в порядке документа: следующий лист — это
следующий кусок текста. Последовательного массива нет: узлы связаны, и
навигация идёт по дереву.

### Узел

```text
a    ветка: индекс левого ребёнка   лист: признак листа | запись
b    ветка: индекс правого ребёнка  лист: позиция
len  ветка: длина поддерева          лист: длина текста
c    ветка: высота поддерева         лист: смещение в источнике
```

Ровно **16 байт**. Вид узла определяется старшим битом `a`, а не
дискриминантом `enum`: обычный `enum` стоил бы 24 байта, потому что восемь ушли
бы на метку, которая здесь не нужна. Индексы узлов и номера записей меньше
`2^31`, поэтому бит свободен.

У ветки кэшируются **длина и высота** поддерева. По ним идёт спуск к позиции
за O(log n): сравниваем позицию с длиной левого поддерева и уходим влево или
вправо. Обходить сегменты не нужно.

Дерево сбалансировано по высоте: высоты соседних поддеревьев отличаются не
больше чем на единицу, иначе делается поворот. Балансировка держит спуск
логарифмическим при любом числе правок.

### Предел по числу сегментов

В памяти живёт не больше **16K сегментов** (`MAX_LEAVES`). Как только порог
превышен, берётся снапшот (§11): дерево схлопывается в новый `Original`, арена
и `Added` очищаются, дерево возвращается к одному листу.

Так память буфера ограничена сверху независимо от того, как долго и как
интенсивно идёт правка. Всё, что старше порога, живёт на диске — отменять
200K сегментов единоразово никто не станет.

### Чтение

Читается обходом дерева слева направо. Для чтения нужна только **ссылка на
текст** — на позиции не смотрят: идёшь по ссылке и читаешь.

| Узел | Что делает читатель |
|---|---|
| лист | читает текст по `text` |

Пропусков нет: удаление вырезает сегменты из дерева, поэтому каждый лист —
текст, который нужно отдать. Байты, вырезанные удалением, остаются в `Original`
и `Added` — их не читают, потому что ссылок на них в `Current` больше нет.

Частичное чтение диапазона идёт с отсечением: поддеревья, целиком лежащие
вне запрошенного диапазона, не обходятся вообще. Стоимость — O(log n) плюс
сам ответ.

Полное последовательное чтение обходится медленнее плотного массива: это обход
дерева, а не один проход по памяти. Редактор полное чтение делает редко — он
рисует видимую часть, — а частичное, которое идёт постоянно, получает дешевле.

## 8. Вставка

Вставка — это диапазон `anchor..head`, где:

* `anchor` — позиция, куда вставлен текст (где началось изменение), всегда
  известна;
* `head` — конец вставленного текста, всегда известен.

Пример. Оригинал `0..11` (11 байт), вставляем на 5-й байт текст длиной 20
байт. Итог: `0-5 | 5-25 | 6-11`.

```text
Original:  0-5  |       5-25       | 6-11
сегменты:  часть  вставленный текст  остаток
```

Сначала идёт текст от 0 до 5, потом вставленный — с 5 до 25, потом остаток
оригинала — с 6 до 11.

Записывается только позиция (якорь) и конец изменения (голова), разница
выходит 20 байт. После изменения начинается следующий сегмент.

**Остальные сегменты обновлять не надо.** Вставил — сказал, где закончился
текст в реальном документе, и всё. В дереве меняется только путь от корня до
точки вставки: лист, в который попали, разрезается на `0-5 | 5-25 | 6-11`, и
ветки на этом пути пересобираются. Остальные листья и ветки не трогаются и не
двигаются — поэтому вставка стоит O(log n) и не зависит от размера документа.

---

## 9. Удаление

Удаление — запись в `undo` (`Delete`, §5), затем **физическое вырезание**
диапазона `anchor..head` из дерева:

* граничные листья обрезаются по границе диапазона;
* полностью покрытые поддеревья уходят из дерева в пул узлов.

Байты никуда не исчезают: они остаются в `Original` и `Added`. Из `Current`
уходит только **ссылка** на удалённый текст — читать его больше не с чего и
нечем. Мёртвых сегментов и пропусков при чтении не бывает.

Как и вставка, удаление меняет только путь от корня до точки правки: O(log n)
поддеревьев пересобирается, остальное дерево не трогается.

Освобождённые узлы не выбрасываются, а идут в пул и используются снова —
поэтому волны вставок и удалений не раздувают память.

---

## 10. Undo / redo

Отмена — это пересборка: верхняя запись `undo` уходит в `redo`, и `Current`
собирается заново линейным проходом по записям `undo` (§7). Ту же работу
делает redo — запись возвращается из `redo` в `undo`, пересборка повторяется.

```text
undo:  запись undo → redo, Current пересобирается
redo:  запись redo → undo, Current пересобирается
```

Пересборка дороже точечной правки — она повторяет операцию каждой записи.
Это осознанная цена за то, что `Current` всегда чистый и без меток.

Записи в `Added` при undo **не трогаются** — текст нужен, если правка вернётся
redo. Физическое удаление текста из `Added` происходит только при очистке
`redo` новой правкой (§3) и при снапшоте (§11).

Состояние документа к моменту отмены в точности то, что было сразу после
отменяемой правки: пересборка повторяет ровно ту же историю.

---

## 11. Снапшот

Правки лежат в памяти, пока это полезно, и выгружаются на диск снапшотами.
Снапшот — это:

```text
1. Собрать чистый текст из Current по ссылкам — это быстро.
2. Собранный текст становится новым Original.
3. На диск выгружаются: вся история, Current, арена, тексты правок.
4. Arena переиспользуется заново.
```

`Current` при сборе **не трогается** — он только читается. Данные из памяти
выгружаются, чтобы их можно было оперативно подменить при отмене, если это
понадобится.

---

## 12. Общий порядок

Любое изменение начинается с записи в `undo`, и только потом обновляется
`Current`:

```text
правка → запись в undo → обновление сегментов Current
```

Память выделяется блоками: арена — новым блоком при переполнении (§4),
`Current` — вектором сегментов. В горячем пути аллокаций нет.
