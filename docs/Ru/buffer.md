# Буфер Claxis

## 1. Назначение

Буфер Claxis предназначен для хранения и редактирования текста с поддержкой:

* вставки;
* удаления;
* замены;
* undo/redo;
* вложенных вставок;
* восстановления текущего состояния;
* последующего хранения истории на диске.

Основная идея — **не изменять исходные данные физически**, а хранить новые данные отдельно и описывать текущее состояние документа через последовательность сегментов.

Буфер состоит из четырёх основных частей:

```text
Original
    +
Add Arena
    +
History
    ↓
Current
```

`Current` является материализованным представлением текущего документа.

---

# 2. Основные компоненты

## 2.1 Original

`Original` — исходное содержимое документа.

Оно:

* immutable;
* не изменяется после загрузки;
* может использоваться как источник сегментов текущего документа;
* не требует копирования при обычных операциях редактирования.

Например:

```text
Original:

abcdefghijklmnopqrstuvwxyz
```

После изменений исходные байты остаются на месте.

---

## 2.2 Add Arena

`Add Arena` — append-only хранилище данных, которые были добавлены в документ.

Каждая новая вставка записывается в arena.

Например:

```text
Original:
abcdefghijklmnopqrstuvwxyz

Add #1:
HELLO

Add #2:
1234
```

Данные из arena физически не удаляются при удалении текста или undo.

Это позволяет:

* не копировать старые данные;
* не выполнять физическое удаление;
* использовать стабильные идентификаторы;
* хранить историю независимо от текущего состояния;
* восстанавливать состояние документа.

Arena может содержать записи, которые больше не участвуют в текущем документе. Это нормально.

---

# 3. Edit / History

Каждое изменение документа представляется операцией в истории.

История является **линейной**.

Основная модель:

```text
undo_stack
redo_stack
```

Активные изменения находятся в `undo_stack`.

Отменённые изменения находятся в `redo_stack`.

### Undo

```text
undo_stack:
[A, B, C]

redo_stack:
[]
```

После undo:

```text
undo_stack:
[A, B]

redo_stack:
[C]
```

Изменение `C` не уничтожается физически. Оно просто перестаёт быть активным и становится частью redo history.

### Redo

```text
undo_stack:
[A, B]

redo_stack:
[C]
```

После redo:

```text
undo_stack:
[A, B, C]

redo_stack:
[]
```

### Новое изменение после undo

Если выполнить новую правку после undo:

```text
undo_stack:
[A, B]

redo_stack:
[C]
```

создаётся `D`:

```text
undo_stack:
[A, B, D]

redo_stack:
[]
```

Redo-ветка удаляется как доступная история.

Физические данные старого `C` в arena при этом могут оставаться до окончания жизни сессии.

---

# 4. Current

`Current` — материализованное представление текущего состояния документа.

Он не является отдельным источником данных.

Источниками данных являются:

```text
Original
Add Arena
History
```

`Current` — это **готовый план чтения текущего документа**.

Например:

```text
Original:
abcdefghijklmnopqrstuvwxyz
```

После вставки:

```text
[
    Original(0..10),
    Add(#1, 0..5),
    Original(10..26),
]
```

Если `Add #1` содержит:

```text
HELLO
```

текущий документ читается как:

```text
abcdefghijHELLOklmnopqrstuvwxyz
```

---

# 5. Current всегда плоский

Ключевая особенность структуры — `Current` не является деревом.

Даже если изменения логически вложены друг в друга, материализованное состояние остаётся плоской последовательностью.

Например, сначала:

```text
Original
    ↓
Add #1
```

Затем внутрь `Add #1` добавляется `Add #2`.

Логически это можно представить как:

```text
Original
    └── Add #1
          └── Add #2
```

Но `Current` хранит:

```text
[
    Original(...),
    Add(#1, ...),
    Add(#2, ...),
    Add(#1, ...),
    Original(...),
]
```

То есть reader не должен рекурсивно обходить:

```text
Original → Add #1 → Add #2
```

Он просто последовательно читает:

```text
Original → Add #1 → Add #2 → Add #1 → Original
```

Глубина логической вложенности поэтому не влияет на алгоритм чтения `Current`.

---

# 6. Вложенные edits

Edit может ссылаться не только непосредственно на `Original`, но и на другой edit или логический сегмент.

Например:

```text
Edit #1:
insert "ABCDEFGHIJ"

Edit #2:
insert "XXXX" inside Edit #1 at offset 5
```

Исторически это может быть представлено как:

```text
Edit #2
    ↓
Edit #1 + offset
```

Однако при построении `Current` эта зависимость разрешается в плоскую последовательность:

```text
Add(#1, 0..5)
Add(#2, 0..4)
Add(#1, 5..10)
```

Таким образом:

**история может содержать зависимости, но механизм чтения текущего состояния не обязан быть рекурсивным.**

---

# 7. Удаление

Удаление не требует отдельного физического объекта данных.

Удаление означает, что определённый диапазон больше не входит в `Current`.

Например:

```text
[
    Original(0..50),
    Add(#1, 0..10),
    Add(#2, 0..4),
    Add(#1, 10..20),
    Original(50..100),
]
```

Если удалить диапазон:

```text
pos = 50
len = 20
```

то соответствующий участок просто исключается из текущего представления:

```text
[
    Original(0..50),
    Add(#1, 0..10),
    Add(#2, 0..4),
    Add(#1, 10..20),
    Original(70..100),
]
```

Данные, которые были удалены, физически не уничтожаются.

---

# 8. Удаление части Original

Если удаляется часть исходного сегмента:

```text
Original(50..100)
```

и удаляется:

```text
70..90
```

получается:

```text
Original(50..70)
Original(90..100)
```

Исходные байты при этом остаются неизменными.

`Current` просто перестаёт ссылаться на диапазон:

```text
70..90
```

---

# 9. Replace

Replace может быть представлен как:

```text
delete + insert
```

Например:

```text
replace(pos, len, data)
```

логически означает:

```text
delete(pos, len)
insert(pos, data)
```

Это позволяет не создавать отдельную фундаментальную модель для replace.

---

# 10. Построение Current

Current может быть полностью пересобран из активной истории.

Упрощённо:

```text
Original
   ↓
active edits
   ↓
Current
```

Построение должно быть последовательным.

Например:

```text
for edit in active_history:
    apply(edit, current)
```

После этого `Current` содержит готовую последовательность сегментов.

Главная цель — чтобы reader не интерпретировал историю при каждом чтении текста.

Вместо:

```text
read()
    ↓
разобрать историю
    ↓
найти нужные edits
    ↓
разобрать зависимости
    ↓
получить данные
```

используется:

```text
read()
    ↓
Current
    ↓
segment
    ↓
Original / Add Arena
```

---

# 11. Линейность

Основное свойство модели:

```text
History:
A → B → C → D → E

Current:
S0 → S1 → S2 → S3 → S4 → ...
```

Обе основные структуры обходятся линейно.

При построении `Current` не требуется дерево поиска.

При чтении `Current` не требуется дерево поиска.

Это уменьшает количество структурных операций и указательных переходов, которые пришлось бы поддерживать в более сложной древовидной структуре.

---

# 12. Arena и размещение данных

Arena является append-only.

Новые записи добавляются в конец:

```text
Arena:

[#0][#1][#2][#3][#4][#5]...
                         ↑
                       append
```

Записи не обязаны удаляться при изменении документа.

Вместо физических удалений используются идентификаторы и диапазоны.

Например:

```text
AddId = 42
range = 100..140
```

`Current` может ссылаться на этот диапазон независимо от того, сколько раз данные вокруг него логически изменялись.

Arena также позволяет использовать стабильные ID вместо необходимости полагаться на физические указатели.

---

# 13. Почему Current не является source of truth

`Current` является кешем/материализованным состоянием.

Если `Current` потерян или повреждён, данные документа не должны быть потеряны.

Его можно построить заново из:

```text
Original
+
Add Arena
+
active History
```

Это важное свойство.

Поэтому оптимизации `Current` не должны менять семантику истории.

---

# 14. Undo/Redo и Current

Undo и redo изменяют набор активных edits.

Например:

```text
History:

A B C D
```

Текущее состояние:

```text
Current = materialize(A, B, C, D)
```

После undo `D`:

```text
undo:
A B C

redo:
D
```

Текущее состояние:

```text
Current = materialize(A, B, C)
```

После redo:

```text
undo:
A B C D

redo:
[]
```

Текущее состояние:

```text
Current = materialize(A, B, C, D)
```

---

# 15. Инкрементальное обновление

Полная пересборка `Current` является базовым и наиболее простым вариантом реализации.

Инкрементальное обновление может быть добавлено позже.

Например:

```text
old Current
    +
new edit
    ↓
updated Current
```

Но инкрементальность не должна усложнять фундаментальную модель без необходимости.

Первичная реализация должна отдавать приоритет:

1. корректности;
2. простоте;
3. предсказуемому поведению;
4. тестируемости.

Оптимизация пересборки может появиться после того, как базовая реализация доказала корректность.

---

# 16. Сложность модели

Важно различать сложность архитектуры и конкретной структуры данных, используемой внутри `Current`.

Создание новой записи в append-only arena не требует перемещения уже существующих данных.

Последовательный переход между уже материализованными сегментами `Current` — простой линейный проход.

Полное чтение документа неизбежно требует времени, пропорционального объёму выдаваемых данных:

```text
O(document size)
```

Это не должно рассматриваться как `O(1)`.

Аналогично, конкретная реализация `Current` может иметь дополнительные расходы.

Например, обычный `Vec<Segment>` при вставке элемента в середину может потребовать сдвига элементов.

Поэтому:

**архитектура не требует конкретной реализации `Current`.**

Она требует, чтобы `Current` представлял собой плоскую материализованную последовательность сегментов.

Конкретная структура хранения может быть выбрана отдельно, исходя из реального workload.

---

# 17. Cache locality

Модель специально избегает необходимости постоянно обходить сложное дерево при чтении.

Основные проходы:

```text
History → Current
Current → output
```

являются линейными.

Сам `Current` может быть компактной последовательностью небольших дескрипторов:

```text
Segment {
    source,
    offset,
    length,
}
```

Данные самих сегментов находятся в `Original` или `Add Arena`.

Arena не гарантирует отсутствие cache miss. Её преимущество в другом:

* append-only размещение;
* отсутствие постоянных отдельных heap allocation;
* стабильные идентификаторы;
* простой lifetime;
* возможность плотного размещения данных;
* отсутствие необходимости физически удалять старые записи.

Реальное cache-поведение зависит от размера рабочего набора и конкретной реализации.

---

# 18. Основные инварианты

Реализация должна соблюдать следующие свойства.

### Original

```text
Original никогда не изменяется.
```

### Add Arena

```text
Arena append-only.
Существующие записи не перемещаются логически.
```

### History

```text
History линейна.
Undo и redo перемещают edits между состояниями активности.
```

### Redo

```text
Новая правка после undo очищает redo history.
```

### Current

```text
Current содержит только активное состояние документа.
Current плоский.
Current не является source of truth.
```

### Delete

```text
Delete исключает диапазон из Current.
Delete не требует физического удаления исходных данных.
```

### Rebuild

```text
Current можно восстановить из Original + Arena + active History.
```

### Reading

```text
Reader читает Current последовательно.
Reader не обязан рекурсивно разрешать историю edits.
```

---

# 19. Тестирование

Основной способ проверки реализации — тестирование инвариантов и семантики операций.

Минимальный набор:

```text
insert
delete
replace

undo
redo

undo → redo
undo → new edit

nested insert
nested delete

insert после insert
delete через границы нескольких segments

rebuild Current

Current после rebuild == Current до rebuild
```

Особенно важно тестировать операции, пересекающие границы сегментов:

```text
Original | Add | Add | Original
          ↑
        delete
```

а также случаи:

```text
Original | Add | Original
      ↑          ↑
    delete      delete
```

и вложенные edits.

---

# 20. Долговременная история

Модель допускает последующее вынесение старой истории на диск.

Вместо хранения всей истории в RAM можно создавать snapshots/checkpoints.

Например:

```text
Original
   ↓
History A
   ↓
Snapshot 1
   ↓
History B
   ↓
Snapshot 2
   ↓
History C
```

После создания snapshot он может стать новой runtime-базой:

```text
Snapshot 2
   +
активная история после Snapshot 2
```

Старые поколения при этом сохраняются отдельно на диске.

Это позволяет иметь потенциально очень длинную историю изменений, не удерживая всю её в оперативной памяти.

Такая система является отдельным уровнем над базовой моделью буфера и не требуется для первоначальной реализации.

---

# 21. Итоговая модель

Вся архитектура буфера сводится к следующей схеме:

```text
                    ┌──────────────┐
                    │   Original   │
                    │   immutable  │
                    └──────┬───────┘
                           │
                           │
                    ┌──────▼───────┐
                    │  Add Arena   │
                    │  append-only │
                    └──────┬───────┘
                           │
                           │
                    ┌──────▼───────┐
                    │    History   │
                    │  undo / redo │
                    └──────┬───────┘
                           │
                           │ materialize
                           ▼
                    ┌──────────────┐
                    │    Current   │
                    │ flat segments│
                    └──────┬───────┘
                           │
                           │ sequential read
                           ▼
                    ┌──────────────┐
                    │    Reader    │
                    │   Renderer   │
                    └──────────────┘
```

Главный принцип:

> **История хранит изменения, arena хранит данные, Original хранит исходное состояние, а Current хранит готовый плоский план чтения текущего документа.**

Именно разделение этих ролей является основой буфера Claxis.
